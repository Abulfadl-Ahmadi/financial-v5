# AI-agent handoff: bank-statement reconciliation for the sewing workshop

**Purpose.** This document transfers the investigative context, source evidence, limitations, and a proposed *review-first* implementation plan. It is **not** an instruction to post the transactions automatically. Another agent should independently inspect the current code, database, and source statements before deciding whether and how to implement these recommendations. The working tree contains substantial unrelated user work: do not reset, overwrite, or quietly migrate it.

## 1. Original request, scope, and what I actually did

The owner had missed several weeks of updates to the site's financial reporting and supplied two bank Excel statements in this directory. They asked me to examine the database and statement formats and extract transactions related to the sewing workshop. I:

1. Read the original two XLSX statements and their first rows/headers. Located the configured Django database in the backend settings, inspected its *actual SQLite tables and records* read-only, and inspected financial/user/sewing models and API behavior.
2. Compared statement destination cards with cards registered to site users, and statement transfer tracking codes, dates, amounts, and source deposits with pre-existing receipts. Recognized that matching a worker's card identifies a payee, **not** the purpose of the payment.
3. Wrote a stand-alone read-only extraction script, [extract_workshop_transactions.py](<extract_workshop_transactions.py>), using `sqlite3` in `mode=ro` and `openpyxl`. It produces a multi-sheet review workbook, [تراکنش‌های-کارگاه-برای-بررسی.xlsx](<تراکنش‌های-کارگاه-برای-بررسی.xlsx>), and a Persian narrative, [گزارش-بررسی-تراکنش‌های-کارگاه.md](<گزارش-بررسی-تراکنش‌های-کارگاه.md>).
4. Verified the statement totals against the printed bank totals; checked exported row counts, internal transfers, payee amounts, and receipt match counts; compiled the extraction script. **I did not import any transaction, create/update any receipt or expense, or intentionally alter the site database.** The generated workbook and the report contain sensitive full card numbers; limit access.

**Critical chronology / stale-context warning.** After that analysis, the working tree and actual SQLite database acquired new, separate Party/card-ownership migrations and data. I rechecked the current state while preparing *this* handoff. The earlier Persian narrative's statement that `users_party` was absent and the migrations were pending became **obsolete**; I have since corrected that paragraph in the Persian file. Use the current-state section below and recheck the database before implementing: these files and migrations are actively changing. The earlier standalone export still uses the legacy `financial_account.user_id` join and has **not** been redesigned for Party-based ownership; the numerical counts in its output remained reproducible on this recheck.

**Verification performed:** I ran the extraction script and `py_compile`, then asserted 1,372 exported bank rows, 76 internal-transfer rows, 110 known-payee rows and their sums, 83 without matched receipts, and a 22/5 exact/probable split. I read the live SQLite tables via `mode=ro` for this handoff. I did **not** run the Django or frontend test suites, because this handoff only changes documentation and the application code has unrelated work in progress. A future implementation must run the relevant test suites.

## 6. Existing extraction implementation: transparent algorithm and limitations

The script [extract_workshop_transactions.py](<extract_workshop_transactions.py>) hardcodes these two bank filenames and expected accounts. It asserts the exact 11-column header and contiguous statement sequence, normalizes Persian/Arabic digits, extracts deposit/withdrawal/reference/document/card tracking/destination card with regex, checks source totals, pairs same-reference opposite-sign internal transfers between the two statements, looks up destination cards in `financial_account` joined to `users_user`, matches existing receipts, then exports classified rows. Classification precedence explicitly puts claimed reversals and uncertain notes **ahead of** worker-card matching; the repair note also precedes generic worker matching. Fees with identical same-account document/reference/date are annotated as possibly linked to a base row but **are not automatically business expenses**. It reads SQLite in read-only URI mode and writes only the review workbook.

This is a **one-off analysis tool**, not a production ingest pipeline. No immutable import batch, raw-row storage, checksum/idempotency key, authorization, migration, transactional writes, reviewer identity/history, bank-format versioning, or exhaustive parsing tests are provided. Its source-card-to-deposit mapping is inferred from fee descriptions; it will fail for other bank formats or absent/changed fee wording. The matching falls back from exact tracking to a unique date/source/destination/amount candidate, which can become ambiguous or collision-prone with future files; enforce uniqueness and human review, never silently merge. Rows without recognized cards may still be business transactions. The final report counts describe this input snapshot and should be recomputed after any source/DB changes.

### P1 — Add a review-first bank-statement import and reconciliation subsystem

Design the schema deliberately. One reasonable approach:

- A `BankDeposit` (or similar) entity with explicitly confirmed deposit number and IBAN, linked to the appropriate owner Party and eligible source payment cards; **do not treat a card number as a deposit number**. Preserve historical assignments and authorization state.
- `BankStatementImport` with account, date range, original filename, SHA-256 content hash, format/version, totals, counts, uploader, timestamp, validation/status, and private file storage policy.
- `BankTransaction` with import FK, source row index, original description and note, normalized Jalali datetime, direction, **integer IRR** amounts and balance, document/reference/tracking codes, parsed destination and source identifiers, linked fee/internal-transfer counterpart, and a stable per-account bank identity. Suggested idempotency: unique `(deposit, bank-verified transaction ID)` where reliable; otherwise a documented canonical fingerprint plus collision handling and `(import, physical source row)` uniqueness. A bank reference alone is **not** globally unique. Keep every original row even if excluded from reporting.
- A separately reviewed `BankTransactionDecision`/posting state and audit log with reviewer, time, rationale, optional evidence file, financial purpose (payroll, advance, reimbursement, maintenance, supplies, revenue, personal, transfer, refund, unknown), and explicit links to existing/new Receipt or Expense/ledger postings. Prevent the same bank principal from creating multiple postings unless intentionally split with sum/reconciliation rules. Distinguish `unreviewed`, `suggested`, `approved`, `rejected`, and `posted`; an ML/text suggestion must never equal approval.
- Optional explicit `Receipt.bank_transaction`/`Expense.bank_transaction` relation(s) or a small posting/link table compatible with existing data and partial/split payments. Constraints should enforce non-duplication and preserve source provenance. Handle refund/reversal and fees separately rather than pretending a negative expense automatically cancels the original entry.

Importer behavior: upload → validate file type/size and exact recognizable headers/deposit/range → parse safely (Persian digits/Jalali, `openpyxl` pinned in backend dependencies if used) → compute signed/balance and bank-header totals → **dry-run preview** → check account/Party permissions → persist staged raw rows in a transaction → detect repeat file and overlapping date range → suggest exact/probable/ambiguous/no matches → human review → explicitly approved posting. No bulk `Expense`/`Receipt` writes simply because a destination card has a worker role. For repeat uploads, stable bank identities and constraints must prevent duplicate principal even if file names/order differ. If source headers change, report a clear error instead of half importing. Give every source row a reproducible provenance reference.
